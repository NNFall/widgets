# 2026-07-26 — Локальный мост Telegram ↔ Codex

Статус: код и Windows-настройка готовы; живая Telegram-проверка ожидает токен
владельца

## Коротко

Подготовлен автономный Windows-мост, с которым сообщение Telegram становится
новым ходом в выбранной задаче Codex. История не копируется в сторонний чат:
используется штатная команда `codex exec resume`, поэтому результат остаётся
видимым и в Codex Desktop.

## Что получилось

- Белый список Telegram user ID до любого запуска Codex.
- Привязка Telegram-чата к конкретному thread ID.
- Переключение между задачами командой `/use <thread-id>`.
- Последовательная SQLite-очередь и защита от повторного `update_id`.
- Восстановление незавершённых ходов и недоставленных ответов после рестарта.
- Межсессионный Windows `Global\` named mutex, не позволяющий второму
  bridge-процессу, включая другую RDP-сессию, повторно забрать выполняющийся ход.
- Разбиение длинного ответа на сообщения до 4 000 символов без потери текста.
- Сохранение delivery cursor после каждого подтверждённого фрагмента.
- Скрытый ввод токена и хранение в пользовательской переменной среды Windows.
- Ручной запуск и Scheduled Task при входе без прав администратора.

## Проверенные факты

- 33 теста моста проходят без обращений к Telegram и Codex.
- `ruff` не находит ошибок в новом Python-коде.
- `compileall` успешно компилирует пакет.
- Все четыре `.ps1` проходят parser Windows PowerShell.
- Токен Telegram удаляется из окружения перед запуском дочернего Codex.
- stderr Codex не записывается в локальный журнал, чтобы не сохранить приватный
  текст сообщения.
- При crash после ответа Codex устойчивый outbox исключает повторный ход; после
  SQLite-записи файл удаляется.
- При таймауте завершается всё дерево `codex.cmd → node`, а не одна оболочка.
- После доставки приватные prompt и response очищаются; каждый час старые
  метаданные удаляются, а освобождённые страницы SQLite очищаются.

Ручной эксперимент до реализации моста подтвердил основной транспортный
контракт: `codex.cmd exec resume --all --skip-git-repo-check <thread-id> <prompt>`
добавил новый ход в указанную историю, а Codex Desktop показал его после
перезапуска.

## Честные ограничения

- В репозитории намеренно нет токена BotFather, Telegram ID и пользовательской
  конфигурации. Поэтому реальный round trip `Telegram → Codex → Telegram` ещё
  не заявляется проверенным.
- В первой версии поддерживается только текст.
- Публикации в Telegram-канал не выполняются. Это отдельный будущий этап с
  явным подтверждением владельца.
- Один worker выполняет ходы последовательно; это защищает историю от двух
  одновременных записей, но длинный ход задерживает следующие сообщения.
- Telegram `sendMessage` не имеет idempotency key. После обычной ошибки
  сохранённый cursor исключает повтор частей; после жёсткого crash в узком окне
  между отправкой и записью cursor может повториться один фрагмент.
- Полный старый suite проекта сейчас содержит один не связанный с мостом сбой:
  браузерный тест ожидает английский статус `running`, тогда как интерфейс уже
  переведён и показывает «Запуск в процессе». Изолированные тесты моста от
  этого расхождения не зависят.

## Возможная публикация после живой проверки

«Раньше я мог продолжать работу только из Codex Desktop. Теперь написал
замечание в Telegram — и оно появилось новым сообщением в той же задаче, со всей
предыдущей технической историей».

До живого теста тема остаётся со статусом `hold`.

## Нужные изображения

1. Сообщение владельца в Telegram-боте.
2. Ответ бота с финальным результатом.
3. Та же пара сообщений в истории Codex Desktop после обновления.
4. Команда `/status` с привязанным thread ID без секретов.
