# Почему публичный сайт упал на редиректе www

Дата: 2026-08-24

Статус: исправлено локально и покрыто тестами; production rollout ожидает
штатного app/worker release.

## Что произошло

Публичный адрес с `www` отдавал обычный канонический редирект на корневой
домен. Защитный crawler Kaigo сравнивал host буквально и принимал этот
безопасный alias за cross-origin robots redirect. Запуск завершался на первом
этапе до вызова модели.

## Что изменено

- разрешена только пара `www.example.com` и `example.com` при одинаковых
  схеме и порте;
- проверка DNS и SSRF-ограничения выполняются для каждого адреса редиректа;
- произвольные поддомены, внешние хосты и приватные адреса остаются
  fail-closed;
- добавлены тесты для robots и document redirect.

## Проверка

- `tests/builder_lab_cases/test_reference_security.py` и
  `tests/builder_lab_cases/test_reference_pipeline.py`: 16 passed;
- реальный crawler-прогон `https://www.cloud.ru/` после патча: `succeeded`,
  четыре desktop и три mobile снимка, оба viewport покрыты полностью;
- полный crawler-файл содержит пять нестабильных browser-fixture падений,
  не связанных с изменением redirect-логики.

## Пользовательский эффект

В старой записи пользователю показывалось только: «Не удалось снять главную
страницу сайта». После выпуска канонический `www`-адрес должен доходить до
получения бесплатного результата. Отдельное улучшение текста для действительно
недоступных сайтов остаётся самостоятельной UX-задачей.
