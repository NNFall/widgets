# Контакты и правовые документы: передача в backend

Статус: предварительный handoff для изолированного frontend-просмотра. Это не
юридическое заключение и не разрешение включать production-сбор. Перед запуском
нужна проверка владельца сервиса и юриста.

## Что есть сейчас

Текущая форма обратной связи только готовит письмо в почтовом приложении
пользователя. Нажатие на `mailto:` ничего не отправляет без отдельного действия
пользователя. Frontend не должен показывать «получено», «доставлено», номер
обращения или успешную отправку, пока настоящий API не вернул такой результат.

Адрес `support@kaigo.space` используется как предварительный адрес в макете. Он
не подтверждает, что почтовый ящик создан, читает письма или является постоянным
каналом поддержки. До production владелец должен подтвердить mailbox и правила
ответа. Telegram также пока не является подтверждённым каналом.

## Будущий `POST /api/feedback`

Публичный контракт нужно согласовать до реализации. Пример тела запроса:

```json
{
  "topic": "question",
  "name": "Необязательно",
  "contact": "Необязательно",
  "message": "Текст обращения",
  "page": "/#contact",
  "consent": {
    "version": "feedback-v1",
    "timestamp": "2026-08-16T12:00:00Z"
  }
}
```

`topic` — обязательный enum только из `question`, `bug`, `improvement`,
`cooperation`. `name` и `contact` — необязательные строки. `message` —
обязательный текст обращения. `page` — нормализованный путь из allow-list, а не
произвольный URL. Версия и время согласия хранятся отдельно от текста
обращения; timestamp принимается только в проверяемом UTC-формате.

Контекст Studio нельзя принимать как готовые права из JSON. Если обращение
идёт из авторизованного Studio, сервер сам получает пользователя, проект и
текущий run из сессии и проверяет их принадлежность. Произвольные
`project_id`, `run_id` или другие идентификаторы из клиента нельзя считать
доказательством контекста. Для landing-контакта контекст проекта/run обычно
отсутствует и должен оставаться `null`.

К запросу нужен ключ идемпотентности (`Idempotency-Key`, idempotency) на
ограниченное время.
Повтор с тем же ключом и тем же владельцем должен вернуть тот же результат, не
создавая второе обращение. Сервер отвечает `202 Accepted` только после
валидации и постановки сообщения в очередь:

```json
{
  "receipt_id": "opaque-server-id",
  "status": "queued"
}
```

`receipt_id` должен быть непрозрачным, не содержать email, текста обращения,
project/run ID или секретов. Ошибки валидации получают обычный 4xx без создания
квитанции; временная ошибка постановки в очередь — 5xx без ложного успеха.

### Защита endpoint

- Ограничить размер JSON, длину `message`, `name`, `contact` и `page`, убрать
  управляющие символы и проверить enum/формат до записи.
- Для браузерной сессии включить CSRF-защиту; запросы из Studio дополнительно
  требуют обычной авторизации. Для публичной landing-формы нужны отдельные
  anti-spam меры и безопасное ограничение анонимного трафика.
- Применить rate limit по IP, сессии и пользователю, лимит очереди, honeypot
  или другой anti-spam контроль и защиту от повторов.
- Не писать в логи тело `message`, имя, контакт, токены и cookies. Допустимы
  request ID, topic, результат проверки, размеры, анонимизированный субъект и
  receipt ID.
- Email и Telegram отправлять только из server-side worker. Bot token, SMTP/API
  credentials и адреса назначения не должны попадать во frontend, HTML,
  архив, логи или ответы API.
- После приёма класть нормализованное обращение в delivery queue. Нужны
  ограниченные повторы с backoff, наблюдаемая причина окончательного отказа и
  dead-letter queue для ручной разборки. Повторная доставка не должна создавать
  второй receipt.
- UI может показывать `queued`, `delivered`, `failed` или кнопку retry только
  после соответствующего ответа API. Mail-only режим остаётся честным и не
  имитирует эти состояния.

## Что нужно подтвердить до production

### Владелец и поддержка

- ФИО или наименование оператора, ИНН, почтовый/юридический адрес и способ
  связи.
- Рабочий `support@kaigo.space` или другой mailbox: владелец должен отправить
  тестовое письмо, подтвердить получение и срок ответа.
- Точный публичный Telegram, владелец канала, правила ответа и хранение
  сообщений. Пока Telegram не подтверждён, ссылку нельзя делать активной.

### Персональные данные

- Определить оператора персональных данных, роли backend, хостинга, почтового и
  AI-процессоров, а также применимость уведомления Роскомнадзора или
  применимое исключение.
- Подтвердить локализацию баз данных в России, трансграничные передачи и список
  обработчиков до включения сбора.
- Зафиксировать цели, категории данных, сроки хранения, удаление, доступ,
  исправление, отзыв согласия и канал для таких запросов.
- Хранить отдельное доказательство согласия: точную версию документа,
  timestamp, субъект/сессию и событие, не подменяя это флагом в UI.

### Оплата и документы

- До оплаты показать оператора, актуальную цену, состав услуги, срок,
  отмену/возврат, способ акцепта и реквизиты. Бесплатный предпросмотр не
  является акцептом платной оферты.
- Подтвердить платёжного провайдера, фискальный сценарий, договор и выдачу
  чека плательщика НПД, если этот режим и обязанность применимы.
- Перед публикацией согласовать все четыре документа (`privacy`, отдельное
  согласие, `terms`, `offer`) с юристом. В тестовой редакции нельзя заявлять,
  что уведомление Роскомнадзора, локализация, срок хранения, платёж или
  оператор уже подтверждены.

В отдельной проверке нужно сверить требования 152-ФЗ и Статья 18.1 с
актуальной редакцией и фактической схемой обработки данных.

reload и включение backend endpoint в рамках этого handoff не выполняются.
