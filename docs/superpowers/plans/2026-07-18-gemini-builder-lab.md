# Фактический план и результат Gemini Builder Lab

## Цель

Создать изолированную лабораторию Kaigo, которая действительно генерирует
премиальный виджет через Gemini по этапам, показывает только проверенные
ревизии, ведёт живой журнал и не затрагивает production-виджеты.

## Принятая архитектура

- Отдельный пакет `builder_lab` и отдельный aiohttp-процесс.
- Прямой staged-движок на `gemini-3.5-flash`.
- Пять стадий: арт-дирекция, каркас, визуальная идентичность, диалог, движение и
  полировка.
- После каждого ответа модель возвращает типизированный JSON-артефакт.
- Детерминированный валидатор проверяет HTML, CSS, доступность, scoped-селекторы,
  размер, URL, анимации и обязательные semantic regions.
- Невалидный кандидат не попадает в preview. Gemini получает коды ошибок и
  максимум две попытки исправления.
- Preview строится фиксированным runtime Kaigo в iframe с `sandbox="allow-scripts"`
  без `allow-same-origin`, внешних запросов и с ограничивающим CSP.
- Прогресс передаётся через SSE реальными событиями orchestrator, а не
  нарисованным таймером.
- Antigravity реализован отдельным адаптером с проверкой скачанного snapshot,
  attestation report, отменой и очисткой удалённой среды.

## Реализованные блоки

1. Типизированные модели request, event, usage, artifact и run snapshot.
2. Конфигурация Gemini, repair-лимитов, TTL, количества запусков и loopback.
3. Валидатор безопасного HTML/CSS и стабильные коды ошибок.
4. Безопасный preview runtime с launcher, suggestions и composer.
5. Gemini Direct Engine со structured output и учётом thinking-токенов.
6. Antigravity adapter с безопасным tar-import.
7. In-memory store с монотонными sequence/revision и SSE replay.
8. Orchestrator со стадиями, repairs, отменой, retry и атомарными terminal events.
9. Двухколоночный Builder UI: настройки и журнал слева, live preview справа.
10. Отдельный Docker Compose profile `builder-lab`.
11. Smoke-скрипт, который требует завершённый run, минимум четыре direct-ревизии
    и положительный расход provider-токенов.
12. Постоянный read-only demo-файл с повторной валидацией перед показом.

## Безопасность и изоляция

- Production-модули `app`, `core`, `wrappers` и `main.py` лабораторией не
  импортируются и не изменяются.
- Builder-контейнер получает только явно перечисленные Gemini-переменные, без
  production `.env`, PostgreSQL и message database.
- Host-порт остаётся `127.0.0.1:8091`.
- Публичная генерация закрывается Basic Auth в nginx.
- Открытое демо имеет только два read-only маршрута и не может вызвать модель.
- Ключи, SSH-данные, proxy-prefix и raw provider errors не записываются в Git,
  demo JSON или browser response.

## Автоматическая проверка

Проверки охватывают:

- контракты моделей и конфигурации;
- все запреты HTML/CSS;
- escape закрывающего `style` независимо от регистра;
- синхронизацию checkbox/CSS toggle в preview runtime;
- Gemini usage и structured output;
- Antigravity download, redirect, attestation, timeout, cancel и cleanup;
- store capacity, TTL, активные runs и terminal races;
- порядок staged events и repair target stage;
- API, SSE replay, CSP и относительные browser URL;
- постоянное демо, атомарное сохранение и повторную валидацию;
- Docker Compose isolation и минимальную версию `google-genai`.

До первой публичной доработки проходил полный набор из 91 теста. После добавления
публичного demo все новые проверки добавляются тем же TDD-циклом.

## Первый реальный Gemini-прогон

Модель: `gemini-3.5-flash` через защищённый Gemini-only маршрут.

Результат:

- статус `run.completed`;
- пять проверенных и зафиксированных ревизий;
- финальная стадия `motion_polish`;
- длительность 407,736 секунды;
- 73 852 входных токена;
- 78 787 выходных токенов;
- 37 365 thinking-токенов;
- 190 004 токена суммарно.

В реальном прогоне сработали repair-циклы: один для арт-дирекции, два для
каркаса, по одному для идентичности, диалога и полировки. Это подтвердило, что
модель не просто выдаёт один HTML, а проходит рабочий цикл «сгенерировать →
проверить → исправить → зафиксировать».

## Серверная проверка

- Feature-ветка развёрнута в `/root/ai_project`.
- `ai_project_builder_lab` работает отдельно от production app/db.
- Production root и `/w/demka` отвечали HTTP 200.
- PostgreSQL был healthy.
- В логах Builder не было свежих traceback/exception/error.
- Браузерная проверка показала ноль console errors/warnings.
- Статический `kaigo.online` не изменялся.

## Актуальный публичный прогон

После ужесточения SVG/motion-проверок и разрешения безопасных нативных
атрибутов выполнен финальный прогон с правильным русским архитектурным брифом:

- `run.completed`, пять ревизий до `motion_polish`;
- 301,260 секунды;
- 46 568 prompt, 52 278 output и 23 517 thinking-токенов;
- 122 363 токена суммарно;
- результат опубликован read-only по `/builder-demo/`.

Контрольный Antigravity-прогон завершился на `agent_build` за 268,846 секунды,
использовал 419 578 токенов и прошёл обе проверки snapshot. Он оставлен
сравнительным доказательством и не заменил direct-демо. После браузерных
исправлений полный набор содержит 103 проходящих теста; Playwright подтвердил
desktop/mobile, интерактивные действия и чистую консоль.

## Вывод

Техническая гипотеза подтверждена: обычный Gemini API достаточен, если вокруг
него есть собственный agent harness со стадиями, строгим контрактом артефакта,
валидацией, repair-циклом, журналом и безопасным runtime.

Главная следующая инженерная задача — снизить задержку и токены. Нельзя в каждом
этапе без необходимости повторно отправлять модели весь накопленный HTML/CSS и
всю историю repairs. После оптимизации лабораторию можно развивать в продукт:
аккаунты, проекты, анализ сайта, durable jobs, версии, публикация и embed-код.
