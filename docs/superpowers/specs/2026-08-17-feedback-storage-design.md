# Серверная обратная связь Kaigo

Дата: 2026-08-17
Статус: утверждённый продуктовый контракт; требуется реализация frontend и backend

## Результат для пользователя

На лендинге и в Studio остаётся одна простая форма. Пользователь выбирает тему,
пишет сообщение и нажимает «Отправить». Имя, телефон, email и другие контактные
данные не запрашиваются. Почтовое приложение не открывается.

Успех показывается только после того, как backend действительно записал обращение
в PostgreSQL. Текст успеха: «Спасибо. Сообщение сохранено и поможет улучшать
Kaigo». Интерфейс не обещает личный ответ, потому что контакт пользователя не
собирается.

`support@kaigo.space` полностью удаляется из интерфейса и документов: почтовый
ящик не создан и его работоспособность не подтверждена. Telegram также не
показывается как пользовательский канал до появления реального публичного
контакта.

## Пользовательский сценарий

Форма содержит:

- четыре темы: вопрос, ошибка, идея по улучшению, сотрудничество;
- одно обязательное поле сообщения длиной от 1 до 4000 символов;
- кнопку «Отправить»;
- короткую подпись со ссылкой на согласие: нажатие кнопки подтверждает обработку
  сообщения по указанной версии документа.

Отдельного поля контакта и отдельного checkbox нет. Юридическая допустимость
такого способа фиксации согласия должна быть подтверждена владельцем и юристом
до production-развёртывания endpoint.

Состояния формы:

1. `idle`: доступен ввод, кнопка активна только при непустом сообщении.
2. `sending`: поля временно заблокированы, кнопка показывает «Отправляем…».
3. `success`: сообщение очищается, показывается подтверждение и действие
   «Отправить ещё».
4. `error`: введённый текст сохраняется, показывается понятная ошибка и кнопка
   «Повторить».

Повтор после сетевой ошибки использует тот же ключ идемпотентности. Новое
сообщение получает новый ключ.

## Frontend-контракт

Frontend отправляет только:

```json
{
  "topic": "improvement",
  "message": "Добавьте возможность…",
  "source": "landing_contact",
  "consent": {
    "version": "feedback-v2",
    "accepted": true
  }
}
```

Допустимые `source`:

- `landing_contact`;
- `studio_account`;
- `studio_auth_error`.

Frontend не отправляет `name`, `email`, `contact`, `project_id`, `run_id`,
`user_id`, IP-адрес или произвольный URL страницы. Контекст Studio backend
определяет из проверенной сессии.

Запрос:

```http
POST /api/feedback
Content-Type: application/json
Credentials: include
X-CSRF-Token: <server token>
Idempotency-Key: feedback-<uuid>
```

Перед первой анонимной отправкой landing получает отдельную сессию:

```http
GET /api/feedback/session
```

Ответ содержит CSRF-токен, текущую версию согласия и максимальную длину
сообщения. Frontend не берёт эти значения из незащищённых query-параметров.

## Backend-контракт

Первая успешно сохранённая запись:

```http
201 Created
Cache-Control: no-store
```

```json
{
  "receipt_id": "fb_opaque_random_value",
  "status": "stored",
  "received_at": "server-generated UTC timestamp"
}
```

Точный повтор с тем же ключом и тем же телом возвращает прежнюю квитанцию без
второй записи. Тот же ключ с другим телом возвращает `409
idempotency_key_conflict`. Frontend считает успехом только валидный ответ
`status: "stored"`; `202 queued` не используется, пока настоящей очереди нет.

Ошибки:

- `400` или `422`: неверная тема, пустой или слишком длинный текст;
- `403`: неверная CSRF-сессия;
- `409`: конфликт ключа идемпотентности;
- `429`: превышен лимит, с `Retry-After`;
- `5xx`: запись не подтверждена, frontend сохраняет текст и предлагает повтор.

## Хранение и история

Основное хранилище — PostgreSQL, таблица `feedback_submissions`. Минимальные
поля:

- внутренний UUID и непрозрачный `receipt_id`;
- тема, текст и источник;
- `user_id` и `tenant_id`, если сессия авторизована;
- server-verified `project_id` и `run_id`, если обращение создано из Studio;
- версия согласия и server-generated `accepted_at`;
- внутренний статус `new`, `reviewing`, `resolved` или `spam`;
- ключ идемпотентности и хеш нормализованного запроса;
- `created_at`, `updated_at`, `purge_after`.

Срок хранения задаётся обязательной production-настройкой и утверждается до
включения endpoint. Текст сообщения не записывается в application-логи. Для
rate limit допустим HMAC-отпечаток IP, но не открытый IP в истории обращения.

Первый backend-релиз не требует операторского кабинета. История доступна
техническому оператору через защищённые серверные инструменты. Будущий закрытый
экран может фильтровать записи по дате, теме и статусу; публичного чтения по
`receipt_id` не будет.

## Telegram позже

Telegram подключается отдельной transactional outbox после сохранения основной
записи. Ошибка Telegram не удаляет обращение и не меняет пользовательский успех.
Bot token и chat ID хранятся только в server-side secrets. Повторная доставка
не создаёт новое обращение.

## Защита

- JSON не больше 16 КиБ, неизвестные поля отклоняются.
- Стартовые ограничения: 5 сообщений за 10 минут на анонимную сессию, 20 в час
  на IP, 30 в час на авторизованного пользователя.
- Для публичной формы используются CSRF, honeypot и rate limit.
- Cookies, токены, текст и персональные данные не попадают в логи.
- Backend сам проверяет принадлежность Studio-проекта и запуска текущему
  пользователю; клиентские идентификаторы не считаются доказательством доступа.

## Компактный footer

Текущий крупный четырёхколоночный блок заменяется обычным малозаметным подвалом:

- компактный знак Kaigo и строка copyright;
- ссылка на обратную связь и четыре правовые ссылки;
- короткая приглушённая строка о статусе оператора и неподтверждённых реквизитах;
- desktop-подача одной горизонтальной переносимой строкой с вертикальными
  отступами 16–20 px и визуальным размером текста 11–12 px;
- mobile-подача в две компактные колонки;
- фактическая область нажатия каждой ссылки остаётся не меньше 44 px.

Несуществующая почта, большой слоган, дублирующая продуктовая навигация и
пятистрочный блок реквизитов удаляются.

## Границы выпуска

Frontend готовится в `codex/product-ui` через TDD. Он не показывает фиктивный
успех без реального backend-ответа. Backend-миграция, endpoint, production
deployment, nginx и сервисы принадлежат техническому чату и оформляются
отдельным `BACKEND REQUEST`.

Изолированный preview v11 остаётся неизменяемым. Обновлённая версия получает
номер v12 только после интеграции реального endpoint либо явно обозначенного
технического preview, который не притворяется production-хранилищем.

## Проверка

- Unit: payload без контактных данных, CSRF, idempotency, `201 stored`, retry и
  сохранение текста при ошибке.
- Component: landing, Studio и auth fallback без mailto и выдуманной почты.
- Accessibility: status/alert, клавиатура, focus, disabled/loading и цели 44 px.
- Responsive: 1920×1080, 1536×960, 390×844 и 320 px без overflow.
- E2E: один POST, отсутствие contact/email/project/run в JSON, честный success
  после backend-ответа и честный error без очистки сообщения.
- Build: typecheck, lint, Vitest, Vite build и `git diff --check`.
