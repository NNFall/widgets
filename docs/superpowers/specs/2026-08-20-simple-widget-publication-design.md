# Упрощённая публикация и установка виджета

Дата: 20 августа 2026 года.

## Цель

Убрать повторный ручной ввод домена из публикации. После подтверждения доступа
пользователь одним действием публикует проверенную версию, сразу получает
постоянную ссылку загрузчика и готовый код установки, а подробности открывает
на публичной странице `/install`.

## Принятый пользовательский путь

1. Пользователь уже указал сайт при создании проекта и проверил виджет.
2. После Founder-пилота или оплаты экран показывает кнопку
   «Опубликовать и получить код» без поля домена.
3. Первая публикация не передаёт `allowed_domains`: backend автоматически
   разрешает точный HTTPS-origin сайта проекта.
4. Обновление существующей публикации сохраняет ранее разрешённые origins,
   включая пустой deny-all список, хотя поле для их редактирования в основном
   сценарии скрыто.
5. Успешная публикация показывает:
   - готовый `<script>` для вставки;
   - постоянную ссылку `embed_url`;
   - отдельные кнопки копирования кода и ссылки;
   - ссылку «Открыть инструкцию по установке» на `/install`.
6. Ошибка публикации объясняет реальную причину без совета «проверьте домены»,
   поскольку пользователь домены больше не вводит.

## Публичная инструкция

Маршрут `/install` доступен без авторизации и не содержит реальных ключей.
Страница объясняет, что пользователь копирует персональный код из Studio, и
даёт короткие проверяемые инструкции для:

- обычного HTML-сайта;
- Tilda;
- WordPress;
- Webflow;
- Wix и других конструкторов с Custom Code / HTML Embed.

Для каждого варианта указаны место вставки, публикация изменений и проверка
кнопки виджета. Примеры используют только placeholder
`https://kaigo.space/embed/YOUR_WIDGET_KEY.js`.

## Безопасность и совместимость

- Origin-защита runtime и visitor chat остаётся fail-closed.
- Виджет не становится общедоступным для встраивания на произвольных сайтах.
- Для нового проекта origin берётся из уже известного `Project.source_url`.
- Для существующей публикации frontend передаёт сохранённый allowlist, чтобы
  обновление версии не меняло рабочие домены.
- Если состояние существующей публикации не удалось восстановить, повторная
  публикация блокируется до успешной перезагрузки. Иначе omission в legacy
  режиме может незаметно заменить custom allowlist на origin сайта проекта.
- Backend API с `allowed_domains` остаётся совместимым для служебных операций и
  canary; меняется только основной пользовательский интерфейс.
- `/install` не принимает stable key через query string и не сохраняет ключи.

## Проверка

1. Component-тесты сначала должны упасть на существующем поле домена,
   отсутствии двух копируемых значений и маршрута `/install`.
2. Frontend-тест проверяет, что первая публикация не отправляет
   `allowed_domains`, а обновление сохраняет серверный allowlist.
3. Backend-тест сохраняет контракт: omitted domains для первой публикации дают
   source origin; чужой origin остаётся запрещён.
4. Browser-проверка выполняется на desktop 1920×1080 и mobile 390×844.
5. Публичный canary на отдельном HTTPS-origin должен загрузить launcher,
   пройти open/close и получить ответ visitor chat; denied origin должен
   остаться заблокированным.

## Вне объёма

- Автоматическое разрешение любого первого увиденного домена.
- Wildcard `https:` или отключение `frame-ancestors`.
- Отдельный конструктор интеграций или плагины для CMS.
- Изменение тарифов, Founder-условий или существующего stable key.
