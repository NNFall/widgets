# Windows-мост Telegram ↔ Codex

Дата: 26 июля 2026 года

Статус: согласовано пользователем

## Цель

Дать владельцу Kaigo возможность писать Telegram-боту и получать ответы из
конкретной задачи Codex. Сообщение должно стать настоящим новым ходом в этой же
истории, а не записью в отдельном чате.

Первая версия передаёт только текст. Изображения, кнопки утверждения публикации и
автоматическая отправка в публичный канал остаются отдельными этапами.

## Выбранный подход

Мост работает как обычный процесс Windows под учётной записью владельца. Он получает
сообщения через Telegram Bot API long polling и запускает для них:

```powershell
codex.cmd exec resume --all --skip-git-repo-check `
  --output-last-message <temporary-file> `
  <thread-id> -
```

Текст передаётся через stdin, а не через shell-строку. `CODEX_HOME` явно указывает на
`%USERPROFILE%\.codex`. Напрямую редактировать rollout JSONL запрещено.

## Компоненты

- `config.py` — загружает несекретную JSON-конфигурацию, раскрывает Windows-переменные и
  проверяет Telegram ID и UUID задач Codex.
- `telegram_api.py` — минимальный HTTPS-клиент `getUpdates`, `sendMessage` и `sendChatAction`.
- `codex_runner.py` — без shell запускает `codex.cmd`, читает только финальный ответ и отделяет
  некритичные предупреждения stderr от реального падения. Финальный output остаётся в
  локальном outbox до подтверждённой записи ответа в SQLite.
- `store.py` — SQLite-очередь, последний подтверждённый `update_id`, привязки чатов и восстановление
  задач после аварийного завершения. Здесь же хранится номер следующего недоставленного
  Telegram-фрагмента.
- `service.py` — авторизация, команды, постановка в очередь и последовательная обработка.
- `instance_lock.py` — межсессионный Windows `Global\` named mutex, не позволяющий
  двум процессам одновременно восстанавливать и выполнять одну очередь.
- PowerShell-скрипты — мастер настройки, ручной запуск и задача Windows Task Scheduler при входе.

## Поток данных

1. Telegram возвращает `Update` с уникальным `update_id`.
2. Мост проверяет `from.id` по белому списку и ищет привязку `chat.id → Codex thread UUID`.
3. Новый текст атомарно попадает в SQLite-очередь; дубль того же `update_id` игнорируется.
4. Один worker берёт одну задачу. Так не появяются два одновременных хода в одной задаче Codex.
5. Финальный ответ сначала сохраняется в SQLite, затем делится на цельные фрагменты не
   длиннее 4 000 символов. После каждого успешного `sendMessage` сохраняется delivery cursor.
6. Только после успешной отправки задача помечается завершённой.

## Команды Telegram

- `/start` — краткая инструкция и Telegram ID для первичной настройки.
- `/status` — текущая привязка и число задач в очереди.
- `/thread` — ID привязанной задачи Codex.
- `/use <uuid>` — меняет привязку для текущего Telegram-чата; доступна только разрешённому
  пользователю.

## Безопасность

- Токен бота берётся только из `TELEGRAM_BOT_TOKEN` и не пишется в репозиторий или логи.
- Входящие сообщения принимаются только от `allowed_user_ids`.
- Процесс наследует права локального пользователя. Telegram здесь является удалённым входом в Codex,
  поэтому белый список обязателен.
- Команда собирается как массив аргументов, `shell=True` не используется.
- Логи не содержат токен бота и полный текст личных сообщений.

## Сбои и восстановление

- При перезапуске задачи со статусом `running` возвращаются в `pending`.
- До восстановления очереди процесс получает межсессионный Windows `Global\` named
  mutex. Второй экземпляр, включая запуск в другой RDP-сессии, завершается и не
  может повторно запустить текущий ход.
- Если Codex уже записал финальный outbox-файл, но процесс упал до SQLite-транзакции,
  следующий запуск использует этот файл и не вызывает Codex повторно.
- Сетевая ошибка Telegram не удаляет задачу; повтор идёт после паузы.
- При частичной отправке длинного ответа повтор начинается с последнего подтверждённого
  фрагмента. Жёсткий crash между ответом Telegram и записью cursor теоретически может
  повторить один фрагмент, потому что `sendMessage` не имеет ключа идемпотентности.
- Ненулевой exit code Codex помечает попытку неудачной и возвращает понятное русское
  сообщение без секретов.
- Предупреждения WebSocket 403 в stderr не считаются падением, если Codex завершился с кодом 0
  и записал финальный ответ.
- При таймауте завершается всё Windows-дерево `codex.cmd`, а не только родительская
  оболочка.
- После доставки prompt и response очищаются. Каждый час завершённые метаданные и
  обработанные updates старше 30 дней удаляются, удалённые страницы SQLite очищаются.

## Запуск в Windows

Мастер настройки создаёт каталог `%LOCALAPPDATA%\KaigoCodexTelegramBridge`, конфигурацию без токена,
базу очереди и лог. Токен задаётся в переменной среды текущего Windows-пользователя. По
желанию создаётся Scheduled Task с триггером при входе. Невидимый Windows service в первой версии не нужен.

## Критерии готовности

- Конфигурация с валидным Telegram ID и thread UUID загружается; ошибочная отклоняется.
- Неавторизованный Telegram-пользователь не может запустить Codex.
- Повторный `update_id` не создаёт второй ход.
- Второй процесс с тем же data directory не может получить очередь.
- Очередь и привязки переживают перезапуск.
- Codex получает текст через stdin и пишет финальный ответ в отдельный файл.
- Длинный ответ без потерь делится на Telegram-сообщения и продолжает частичную доставку
  с сохранённого cursor.
- Новый модуль проходит изолированные тесты без вызова Telegram и без расхода токенов Codex.
- Русская инструкция показывает настройку новой задачи Codex без изменения кода.
