# Компактный лендинг, OAuth и гибридный роутинг моделей

Дата: 2026-07-29  
Статус: согласовано пользователем к реализации

## Цель итерации

Одной проверяемой итерацией исправить первый экран Kaigo для Windows-масштаба 125%, вернуть согласованное B2B-позиционирование, подготовить понятный вход через OAuth и включить гибридную цепочку GPT-5.5 + GLM-5.2 в production worker.

## 1. Первый экран

Основной заголовок:

> Через 10 минут вы сможете сказать: наш бизнес использует AI

Подзаголовок должен объяснять действие и бесплатный первый результат без обещания гарантированного времени для любого сайта:

> Добавьте ссылку — Kaigo изучит страницы, услуги, стиль и вопросы клиентов, а затем бесплатно создаст первую версию персонального AI-виджета.

Кнопка остаётся прямой: «Получить бесплатную версию».

Физический дисплей 1920×1200 при системном масштабе Windows 125% воспроизводится как CSS viewport 1536×960. На этом размере должны одновременно помещаться заголовок, описание, форма, три карточки процесса и макет сайта. Карточки процесса не должны перекрывать макет браузера. Проверка добавляется как геометрический browser-тест, а не как сравнение исходного CSS.

## 2. OAuth

Текущая серверная схема сохраняется: база хранит состояние OAuth и сессии, state привязан к браузерной сессии, Google использует PKCE и nonce.

Для первого ручного запуска выбираем один провайдер. Самый короткий новый путь — Яндекс ID: приложение типа «Для авторизации пользователей», платформа «Веб-сервисы», точный callback `https://kaigo.space/api/auth/yandex/callback`, доступ к основной информации и email.

Сервер должен безопасно обрабатывать отказ провайдера и ошибку обмена токена: не показывать пользователю необработанный HTTP 500 и не раскрывать диагностические данные. Студия получает короткий код ошибки и показывает понятное сообщение с предложением повторить вход. Реальные Client ID и secret остаются только в production `.env` и не попадают в Git.

## 3. Гибридная цепочка моделей

Решения и реализация разделяются по ролям:

| Роль | Модель |
| --- | --- |
| три предложения направления | GPT-5.5 |
| независимый выбор направления | GPT-5.5 |
| план композиции | GPT-5.5 |
| art-direction artifact, foundation, identity, conversation, motion | GLM-5.2 |
| детерминированные и визуальные repair | GLM-5.2 |
| текстовый visual judge и проверка исправления | GPT-5.5 |
| снимки исходного сайта и три критика с изображениями | Gemini, временно |

Последняя строка — осознанное техническое ограничение: проверенный AgentRouter/Qwen-адаптер принимает structured text, но отклоняет binary image inputs. Убирать скриншоты ради формального перехода на две модели нельзя. Когда появится проверенный мультимодальный AgentRouter-провайдер, Gemini в этих ролях можно заменить отдельной конфигурацией.

Production worker получает отдельные переменные AgentRouter, модели решений и реализации, цены и timeout. Секрет обязателен только при включённом гибридном режиме. Роутер продолжает фиксировать provider/model/role/tokens/cost для каждого вызова.

## 4. Учёт токенов

В замороженном сравнении GLM-5.2 получил 220 294 входных токена, GPT-5.5 — 109 645. Разницу создало не повторное сканирование сайта: evidence и composition были одинаковыми. GLM дополнительно списал 170 556 входных токенов на четырёх невалидных structured-ответах. Принятые GLM-вызовы содержали 49 738 входных токенов. Формула совпадает с итоговой разницей:

`170 556 + (49 738 - 109 645) = 110 649`.

Будущие benchmark-артефакты должны сохранять роль, модель, размер и hash промпта, usage и безопасный класс ошибки по каждой попытке, чтобы отличать рост промпта от внутренних ходов клиента.

## 5. Критерии готовности

- unit-тесты подтверждают новый текст и безопасное OAuth-сообщение;
- browser-тест на 1536×960 подтверждает отсутствие горизонтального overflow и пересечения карточек с макетом сайта;
- тесты роутера подтверждают GPT-роли решений и GLM-роли кода/repair;
- мультимодальные роли не направляются в text-only AgentRouter;
- production-сборка и миграции проходят без секретов в репозитории;
- опубликованный `kaigo.space` проверен во встроенном браузере на 1536×960 и 1920×1080;
- реальный OAuth завершается пользователем после добавления Client ID/secret в консоли провайдера.
