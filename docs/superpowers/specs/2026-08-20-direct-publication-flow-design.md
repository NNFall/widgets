# Прямая активация и публикация виджета

Дата: 20 августа 2026 года.

## Цель

Свести публикацию к двум понятным состояниям в одном большом окне:

1. пользователь выбирает бесплатный Founder-пилот или платный тариф;
2. после активации Kaigo сам публикует проверенную версию и сразу показывает
   код установки, постоянную ссылку загрузчика и подробную инструкцию.

Промежуточный экран «Всё готово к публикации» и повторная кнопка публикации
после успешной активации больше не нужны.

## Подтверждённая причина текущей ошибки

Founder-доступ для тестового проекта был успешно создан, а проект содержит
активную проверенную версию. Ошибка возникла на следующей границе релиза:

- новый статический frontend при первой публикации намеренно не отправляет
  `allowed_domains`, чтобы backend сам взял безопасный HTTPS-origin сайта
  проекта;
- работающий production backend относится к предыдущему релизу и всё ещё
  требует `allowed_domains` в versioned request body;
- поэтому три автоматические попытки публикации завершились HTTP 400
  `invalid_body` до входа в `PublicationService`.

Исправление должно выпустить frontend и backend как один совместимый контракт.
Founder grant, подписку, проект и артефакт повторно создавать не требуется.

## Рассмотренные варианты

### 1. Только backend hotfix

Исправляет HTTP 400, но сохраняет лишний экран и вложенный модал. Пользователь
по-прежнему не понимает, почему после «активировать и опубликовать» видит ещё
один этап.

### 2. Автоматически открывать существующий вложенный offer dialog

Убирает первый клик, но оставляет два модальных слоя, раздельные заголовки и
резкий возврат в нижний слой при ошибке.

### 3. Единый state-driven flow

Выбранный вариант. Внешний полноразмерный `StudioDrawer` остаётся единственной
диалоговой поверхностью. Внутри последовательно меняется содержимое: условия,
активация и публикация, установка. Это соответствует пользовательскому
намерению и упрощает ошибки, фокус и responsive layout.

## Пользовательский путь

### Состояние 1. Выбор доступа

Кнопка «Опубликовать» в Studio сразу открывает полноразмерное окно с условиями,
без промежуточной кнопки «Выбрать доступ».

Верхний блок объясняет результат: после выбора доступа Kaigo опубликует текущую
проверенную версию и подготовит код установки. Далее выделен Founder-пилот:

- фактический срок, количество мест и лимит берутся из server offer;
- основной текст для текущего предложения: «14 дней полностью бесплатно»;
- карта не требуется, списаний и автопродления нет;
- ранний доступ даётся в обмен на честную обратную связь о работе,
  недостатках и нужных доработках;
- основная кнопка: «Активировать бесплатно и продолжить».

Платные планы находятся ниже или справа как явная альтернатива. Цены, периоды,
токены и условия продления остаются server-driven. Founder не маскируется под
обычный тариф, а платный вариант не выглядит обязательным.

### Переход. Активация и публикация

После Founder claim или подтверждения оплаты окно не закрывается и не
возвращается к промежуточному экрану. Оно показывает один последовательный
статус:

1. «Активируем доступ»;
2. «Публикуем проверенную версию»;
3. «Готовим код установки».

Повторные клики блокируются. Повторная доставка ответа или восстановление
страницы должны использовать существующие idempotency и publication recovery
контракты.

### Состояние 2. Установка

После успешной публикации то же окно показывает:

- подтверждение «Виджет опубликован»;
- основную кнопку «Скопировать код установки»;
- отдельную кнопку «Скопировать ссылку загрузчика»;
- оба значения в читаемом ручном fallback, если Clipboard API недоступен;
- заметную ссылку «Открыть подробную инструкцию» на `/install`;
- короткое объяснение, куда передать код и что будущие обновления останутся на
  том же постоянном адресе.

Подробности release ID, artifact ID и rollback остаются во вторичном
developer/details-блоке и не конкурируют с основным действием.

## Ошибки и поддержка

- Ошибка активации остаётся на экране выбора доступа и не создаёт впечатление,
  что Founder уже подключён.
- Ошибка публикации после успешной активации показывает отдельное состояние
  «Доступ подключён, публикация не завершена» и кнопку «Повторить публикацию».
- `invalid_body` от несовместимого backend больше не возможен после совместного
  релиза; regression-тест фиксирует optional `allowed_domains`.
- `publication_invalid`, conflict, unverified identity и upgrade-required
  сохраняют безопасные русские сообщения без вывода внутреннего backend text.
- «Расскажите, как прошёл пилот» и Founder feedback доступны только после
  успешной публикации. При ошибке показывается техническая помощь
  «Связаться с Kaigo», не просьба об отзыве.

## Компоненты

- `UpgradeGate` остаётся владельцем billing/publication orchestration, recovery
  и API state.
- `PublicationOfferDialog` преобразуется из самостоятельного вложенного dialog
  в чистое представление условий внутри внешнего окна. Оно не управляет
  backdrop, Escape или закрытием `StudioDrawer`.
- Установочный handoff выделяется в отдельное представление, чтобы основной
  orchestration-компонент не продолжал расти.
- `StudioDrawer` остаётся единственным доступным `role="dialog"` и владельцем
  фокуса, Escape и backdrop.

## Визуальная система

Это продуктовый, а не рекламный экран. На desktop используется широкая
предсказуемая сетка с одной доминирующей Founder-секцией и компактной платной
альтернативой. На mobile все блоки идут одной колонкой.

- основной текст ограничен примерно 70 знаками в строке;
- действия имеют цель касания не меньше 44 px;
- интерактивные ссылки подчёркнуты и имеют заметный focus ring;
- статус загрузки меняет содержимое, а не двигает layout;
- ошибки используют собственный спокойный блок и не окрашивают весь экран;
- окно не содержит декоративных пустых областей или вложенных одинаковых cards.

## Безопасность и совместимость

- Первая публикация не передаёт `allowed_domains`; production backend должен
  принимать omission и выводить точный HTTPS-origin из `Project.source_url`.
- Обновление существующей публикации передаёт восстановленный allowlist,
  включая пустой deny-all список.
- Если publication recovery не завершён, обновление блокируется.
- `/install` не принимает stable key из query и не хранит пользовательские
  ключи.
- Backend и frontend выпускаются одной immutable release-версией; static-only
  release запрещён, если API request contract изменился.

## Проверка

1. RED frontend-тесты фиксируют отсутствие промежуточной кнопки и вложенного
   dialog, непрерывный Founder claim → publish → install flow и корректную
   ошибку после claim.
2. RED backend contract воспроизводит HTTP 400 старого production backend на
   omitted domains и становится GREEN после совместимого route contract.
3. Component-тесты проверяют Founder copy, платную альтернативу, busy state,
   feedback visibility и clipboard fallback.
4. Полный frontend suite, typecheck, lint и build проходят.
5. Publication backend suite и exact-origin security regressions проходят.
6. Во встроенном браузере проверяются desktop 1920×1080 и mobile 390×844:
   offer, loading/error, install handoff, отсутствие горизонтального overflow,
   фокус и кликабельность ссылок.
7. Production canary подтверждает единый request contract, создание release,
   загрузку одного iframe на разрешённом внешнем origin и повторное открытие
   виджета.

## Вне объёма

- изменение цены, срока или лимита Founder-пилота;
- ослабление exact-origin защиты;
- автоматическая публикация до явного нажатия пользователем кнопки публикации
  в Studio;
- CMS-плагины или конструктор доменных allowlist;
- запрос отзыва до успешной публикации.
