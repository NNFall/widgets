# Прозрачная визуальная проверка и восстановление Builder Lab

## Цель

Builder Lab должен объяснять каждое замечание визуальной проверки, не зацикливаться
на одной технической ошибке, сохранять последний работоспособный черновик и
восстанавливать текущий запуск после обновления страницы.

## Подтверждённые проблемы текущей версии

1. Три независимых визуальных критика запускаются, но их результаты объединяет
   Python по совпадению screenshot, категории, semantic region и artifact fields.
   Отдельного AI-судьи, который сопоставляет смысл замечаний, нет.
2. Одиночный blocker сейчас может отправиться в repair без подтверждения второго
   критика.
3. Browser repair, visual repair и исправление детерминированной валидации используют
   один счётчик из пяти попыток.
4. Полный JSON критики записывается во внутренний diagnostic, но diagnostic не
   сериализуется в SSE/API. Пользователь видит только число проблем.
5. Неподтверждённая пятая ревизия хранится отдельно, но snapshot и preview показывают
   только последнюю опубликованную четвёртую ревизию.
6. Идентификатор запуска хранится только в JavaScript-переменной и пропадает при
   reload.
7. Статус и art direction обрезаются CSS-ellipsis.

## Архитектура визуального цикла

### 1. Три независимых критика

`conversation_ux`, `brand_motion` и `adversarial_customer` по-прежнему получают
одинаковые браузерные доказательства и выполняются параллельно. Каждый возвращает
строгий JSON с наблюдениями и замечаниями.

После завершения в публичную ленту попадает отдельное событие каждого критика:
роль, краткий вывод, видимый факт, screenshot, серьёзность и предлагаемое исправление.
Приватные provider diagnostics и внутренние chain-of-thought не публикуются.

### 2. Независимый AI-судья

Новый `GeminiVisualJudge` получает три независимых JSON-ответа, но не получает
возможность изменять виджет. Судья семантически объединяет замечания, даже когда
они написаны разными словами.

Каждое принятое замечание обязано:

- ссылаться на существующие `finding_id`;
- содержать минимум две разные роли;
- использовать только screenshot, категории и artifact fields из исходных замечаний;
- содержать одно конкретное объяснение и одну проверяемую инструкцию исполнителю.

Одиночное замечание любого уровня, включая blocker, сохраняется в отчёте, но не
запускает автоматическое исправление. Если валидны менее двух критиков или судья не
вернул проверяемый контракт, результат называется `visual_review_inconclusive`.

### 3. Исполнитель

Один запрос Gemini получает цельный список подтверждённых судьёй проблем и текущий
артефакт. Он возвращает обновлённый артефакт и `change_summary`.

`change_summary` должен быть написан для обычного пользователя:

- без CSS-селекторов, имён атрибутов, фрагментов кода и hex-цветов;
- перечислять, какие видимые проблемы исправлялись;
- в одном-трёх коротких предложениях объяснять результат.

### 4. Независимый code-verifier

Новый `GeminiRepairVerifier` получает подтверждённые замечания и ограниченный diff
до/после. Он не изменяет код. Для каждого `finding_id` он возвращает `fixed` или
`unresolved` с конкретным доказательством из diff.

Результат verifier публикуется в ленте. После него всегда выполняется новый
детерминированный browser audit и новый независимый цикл трёх критиков: окончательная
истина остаётся за браузером и новыми изображениями.

## Независимые бюджеты и защита от зацикливания

- Browser capture retries: 6 на неизменённый кандидат.
- Browser defect repairs: 4.
- Deterministic contract repairs: 4.
- Visual repairs: `visual_repair_limit`, по умолчанию 8, максимум 10.
- Critic response attempts: 3.
- Judge response attempts: 3.
- Verifier response attempts: 2.

Счётчики не уменьшают друг друга. Повтор одного и того же подтверждённого судьёй
семантического замечания допускается не более трёх раундов. После этого автоматический
цикл останавливается с понятным отчётом и сохраняет черновик, вместо бессмысленного
расходования токенов.

Зарезервированные `data-kaigo-runtime-message`, `data-kaigo-runtime-label` и
`data-kaigo-runtime-content` удаляются детерминированно из статического HTML. Для
этой известной технической нормализации отдельный запрос Gemini не используется.
Остальные ошибки контракта сохраняют отдельный deterministic repair budget.

## Черновик при непрошедшей проверке

Store отдельно хранит:

- `artifact` — последнюю опубликованную и полностью проверенную ревизию;
- `draft_artifact` — последний кандидат, прошедший детерминированную валидацию, но
  ещё не прошедший все publication gates.

Snapshot возвращает оба значения и `quality_status`. Builder preview может показывать
`draft_artifact` только как экспериментальный черновик. Chat/refine/publish продолжают
использовать только проверенный `artifact` до отдельного разрешения.

Если visual gate исчерпан, пользователь видит последний валидный draft с пометкой
«Требует доработки», полным списком оставшихся проблем и кнопкой повторного запуска
доработки.

## Восстановление после reload

Страница сохраняет opaque run ID в `localStorage` сразу после создания, retry или
refine. При загрузке она:

1. читает только собственный ключ Builder Lab;
2. запрашивает snapshot;
3. восстанавливает source URL, brief, telemetry, preview и состояние кнопок;
4. заново подключается к SSE с начала истории, чтобы восстановить всю ленту;
5. удаляет ключ только при `404 run_not_found`.

Reload не отменяет серверную задачу и не создаёт новый запуск.

## Интерфейс

- Status и art direction переносятся на несколько строк без ellipsis.
- События отображают `issues` полным списком.
- Сообщение `artifact.committed`, visual repair и verifier используют понятные
  пользовательские формулировки.
- Для draft показывается отдельная маркировка; публикационный статус не смешивается
  с возможностью локального preview.

## Проверка

Полноценный Gemini-прогон не выполняется. Проверка включает:

- unit-тесты судьи, verifier и раздельных бюджетов;
- store/web-тест draft preview;
- browser integration с искусственно созданным running run: записать ID, reload,
  убедиться, что история, статус и preview восстановились;
- browser integration терминального failed run с доступным draft;
- полный локальный test suite, compileall и `git diff --check`;
- развёртывание точного commit и повтор коротких browser-сценариев через встроенный
  браузер.
