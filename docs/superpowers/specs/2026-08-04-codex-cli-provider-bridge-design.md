# Codex CLI bridge для генератора Kaigo

## Цель

Добавить в Kaigo экспериментальный внутренний провайдер, который использует уже
авторизованный Codex CLI на нидерландском сервере. Первая версия должна доказать,
что `gpt-5.6-luna` с уровнем reasoning `max` стабильно создаёт структурированные
ответы, продолжает диалог между этапами и анализирует скриншоты виджета.

Это не замена всей существующей маршрутизации моделей. Провайдер включается
feature-флагом и может быть отключён без изменения пользовательских запусков,
артефактов и текущего Gemini/AgentRouter fallback-контура.

## Подтверждённая среда

- Codex CLI установлен на нидерландском сервере и авторизован через ChatGPT.
- Текущая версия CLI — `0.144.5`; перед тестом она обновляется до актуальной
  опубликованной версии и перепроверяется командой `codex --version`.
- Каталог сервера содержит `gpt-5.6-luna` с reasoning `low`, `medium`, `high`,
  `xhigh`, `max` и входными модальностями `text`, `image`.
- CLI поддерживает `codex exec --json`, `codex exec resume`, `--output-schema`,
  `--image`, `codex archive` и `codex delete`.
- Первый диагностический запуск Luna Max на старой версии CLI не завершился за
  две минуты. Поэтому timeout, корректное завершение дочернего процесса и
  ограничение конкурентности входят в обязательный MVP, а не откладываются.

## Архитектура MVP

На хосте запускается отдельный процесс `kaigo-codex-bridge`. Он не принимает
публичные HTTP-запросы. Builder worker обращается к нему через Unix-сокет,
доступный только сервисам Kaigo.

Bridge использует обычные subprocess-вызовы, а не beta SDK и не долгоживущий
Codex App Server:

1. Первый turn запускается через `codex exec --json`.
2. Bridge читает JSONL до `turn.completed` или `turn.failed` и сохраняет
   `thread_id` из `thread.started`.
3. Следующий turn запускается через `codex exec resume <thread_id> --json`.
4. JSON Schema передаётся через `--output-schema`; финальный ответ дополнительно
   валидируется существующим Python-кодом Kaigo.
5. Скриншоты визуального аудита передаются Luna через `--image`.
6. После терминального состояния запуска Codex-сессия удаляется из активного
   списка. В MVP используется архивирование; после подтверждения восстановления
   из собственного журнала можно переключить политику на немедленный
   `codex delete <thread_id> --force`.

Bridge реализуется как отдельный адаптер к существующему `ModelProvider` и не
ломает `ModelRouter`, учёт вызовов, fallback-цепочки или текущие контракты
артефактов.

## Диалоги и ключи сессий

Один параллельный model turn не должен блокировать другой. Поэтому используется
не один общий thread на весь виджет, а несколько логических conversation keys:

- `build` — последовательные стадии создания и доработки артефакта;
- `direction:<candidate_id>` — три независимых предложения направления;
- `direction:judge` — выбор направления;
- `critic:<persona>` — каждый независимый визуальный критик;
- `visual:judge` — объединение замечаний;
- `repair` и `repair:verify` — исправление и независимая проверка;
- `reference` — анализ исходного сайта.

Соответствие `(run_id, conversation_key) -> thread_id` хранится bridge-процессом
и переживает его штатный перезапуск. Builder передаёт `run_id`, роль, стадию,
candidate/persona и semantic attempt как служебные metadata; они не добавляются
в пользовательский текст.

## Конкурентность и таймауты

- Одновременно выполняются не более трёх subprocess-вызовов Codex.
- Для одного `thread_id` действует single-writer lock: два turn одного диалога
  никогда не запускаются параллельно.
- Остальные запросы ожидают в ограниченной очереди.
- Каждый процесс имеет soft timeout и короткий grace period, затем завершается
  вся его process group.
- Timeout, повреждённый JSONL, отсутствие `thread.started`, невалидный итоговый
  JSON и отказ модели превращаются в существующие типизированные provider errors.
- После такой ошибки `ModelRouter` может перейти к следующему настроенному
  target; незавершённый Codex-процесс не остаётся на сервере.

Для первого контрольного прогона Luna всегда запускается как
`gpt-5.6-luna` с `model_reasoning_effort=max`. Оптимизация уровня reasoning по
ролям выполняется только после измерения качества и времени полного виджета.

## Изоляция

Codex запускается в отдельной директории конкретного run, с read-only sandbox и
approval policy `never`. Shell, unified exec, apps, multi-agent и web search
отключаются. На вход передаются только подготовленный prompt, JSON Schema и
явно выбранные изображения. Пользовательский URL или контент сайта не может
заставить Codex читать произвольные файлы сервера или выполнять команды.

ChatGPT credential остаётся в `$CODEX_HOME` хоста и не монтируется в основной
web-контейнер. Bridge никогда не возвращает auth-файлы, токены или полный stderr
в пользовательский API.

## Журналирование и удаление

История Kaigo не зависит от списка сессий Codex. Bridge формирует собственный
JSONL-поток со следующими безопасными событиями:

- run, conversation key, thread id и turn id;
- начало, завершение, timeout и типизированная ошибка;
- публичные agent messages и финальный структурированный результат;
- агрегированное usage, latency, модель и reasoning level;
- ссылки на уже существующие Kaigo screenshots и artifacts.

Auth-данные и скрытые рассуждения не сохраняются. На первом этапе JSONL нужен
для проверки оболочки и диагностики. Его полноценное помещение в пятидневное
forensic-хранилище и интерфейс воспроизведения являются следующей итерацией.

После завершения бесплатной генерации или иного терминального сценария bridge
архивирует связанные Codex threads, поэтому они не засоряют активную историю.
Когда собственный журнал доказал достаточность для диагностики, политика может
удалять Codex threads немедленно, сохраняя только журнал Kaigo.

## Проверка MVP

1. Обновить CLI и подтвердить ChatGPT login без вывода credential.
2. Проверить каталог: Luna, `max`, `text` и `image`.
3. Текстовый тест: создать thread, получить строгий JSON, продолжить тот же
   thread вторым turn и доказать сохранение контекста.
4. Визуальный тест: передать существующий screenshot виджета и получить строгий
   отчёт критика со ссылкой на видимые элементы.
5. Запустить три независимых тестовых turn одновременно и доказать, что
   четвёртый ждёт, а один conversation key остаётся последовательным.
6. Смоделировать timeout и убедиться, что process group исчезла, ошибка
   типизирована, а очередь продолжила работу.
7. Завершить тестовый run, архивировать его threads и убедиться, что собственный
   JSONL остался читаемым.
8. После этих проверок подключить Codex target к одному контрольному запуску
   Builder через feature-флаг; публичный трафик автоматически на него не
   переводить.

## Вне первой итерации

- Использование ChatGPT-authenticated CLI как единственного публичного
  production-провайдера без отдельной проверки лимитов и условий использования.
- Удобный web-интерфейс просмотра и повторного импорта сохранённой истории.
- Долгосрочное хранение полных prompts и ответов.
- Оптимизация reasoning level, стоимости и распределения ролей до получения
  измерений контрольного прогона.
