# Свежие Codex-диалоги для repair-вызовов

## Проблема

Сейчас `conversation_key` для роли `repair` равен `repair:<stage>`. Все исправления
одного этапа продолжают один Codex thread. При этом каждый repair-prompt уже содержит
полный текущий артефакт и актуальный список ошибок. Предыдущие неудачные ответы не
нужны, но повторно попадают во входной контекст и увеличивают время и расход токенов.

## Решение

Сохраняем текущие диалоги основных этапов, кандидатов направления и критиков. Только
для `repair` и `code_review` формируем одноразовый ключ из:

- роли;
- этапа генерации;
- UUID конкретного логического модельного вызова, который router создает до отправки
  провайдеру.

Пример: `repair:motion_polish:<logical-invocation-id>`.

Так каждый самостоятельный repair-prompt запускается через новый `codex exec`, без
`resume`. Повторные provider fallback-вызовы одного и того же логического запроса
используют тот же ключ: это одна операция, а не новая итерация исправления.

## Контракт

- repair-prompt остается самодостаточным: текущий HTML/CSS/JS, выбранное направление,
  необходимые паттерны и только актуальные ошибки;
- роль `repair` в учете моделей не меняется;
- новый логический repair-вызов не может возобновить thread предыдущего вызова;
- некорректные или отсутствующие lineage-поля обрабатываются безопасным хешированным
  сегментом;
- завершение run архивирует все созданные одноразовые threads штатным механизмом.

## Критерии успеха

1. Два последовательных логических repair-вызова получают разные `conversation_key`.
2. Provider fallback одной логической операции сохраняет тот же ключ.
3. Обычные build/critic/direction ключи не меняются.
4. Bridge не добавляет `resume` для следующей repair-попытки.
5. В контрольном прогоне входные токены repair-вызовов не растут из-за накопленной
   истории предыдущих исправлений.
