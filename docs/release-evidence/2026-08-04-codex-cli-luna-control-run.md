## Почему запуск считался неуспешным

Финальный browser gate четыре раза сообщал одинаковые ложные ошибки:

- `desktop.open_initial: panel is clipped`;
- недоступными считались кнопки закрытия, отправки и быстрых вопросов;
- недоступными считались области панели.

Корневая причина находилась не в сгенерированном виджете. Виджет использует нормальный безопасный шаблон:

```css
.kaigo-widget {
  position: fixed;
  inset: 0;
  pointer-events: none;
}

.kaigo-widget__panel,
.kaigo-widget__launcher {
  pointer-events: auto;
}
```

Старый аудит ошибочно наследовал `pointer-events: none` от корневого контейнера и объявлял интерактивные дочерние элементы заблокированными. Исправленный аудит проверяет реальную доступность целевого элемента через hit-test и больше не считает такой корень дефектом.

Точный HTML сохранённой revision 5 после исправления прошёл локальный BrowserAudit:

- 6 снимков;
- 8 проверенных состояний интерфейса;
- результат: `PASS`.

То есть сохранённый виджет визуально работоспособен, а исторический красный статус относится к старой версии проверяющего кода.

## Ограничения текущей версии

1. В Studio в селекторе всё ещё отображается старое пользовательское название `Gemini staged`, хотя production-сборка идёт через Codex Luna Max. Это визуальная подпись фронтенда, не реальный маршрут.
2. Grounding для посетительского чата недостаточно подробный: транспорт работает, но ответы могут избегать конкретики.
3. Нужен один новый полный контрольный прогон уже на исправленном worker, чтобы измерить реальное сокращение времени и токенов. Исторический прогон повторно не запускался, чтобы не расходовать ресурсы без необходимости.

## Следующий практический шаг

1. Переименовать модельный режим в Studio в понятное нейтральное название, соответствующее реальному маршруту.
2. Запустить один новый контрольный сайт на исправленной production-версии.
3. Сравнить время и токены по этапам с этим baseline.
4. Затем сокращать самые дорогие этапы и усиливать grounding посетительского чата.
